PAIN POINT 01 // 传统 BI 报表的局限
“只给图表，不给归因与缺失保护”
  • 聚合抹平斜坡趋势：只给周期汇总，看不出 S001 自 10月6日起连续 3 天渐进式滑坡。
  • 规模与效率混为一谈：销售额下滑未拆解为订单数 × 客单价双因子，误把客流波动当客单问题。
  • 最危险的“假阴性”：如 S004 退款字段断报（空值率 33%），传统报表直接算作 0 异常，掩盖严重故障。
❌ 症结：有数字无洞察，数据断报时产生致命“假阴性”误导
PAIN POINT 02 // 通用大模型 / Text-to-SQL 的风险
“口径幻觉、乱算比率与强行归因”
  • 比率口径算错：LLM 自由写 SQL 经常直接 AVG(daily_ratio) 平均每日比率，违背“先 SUM 聚合再算比率”铁律。
  • 样本不足强行定论：当同业态可比门店 < 3 家 或南关区缺租金数据时，通用 AI 仍会编造回本周期与根因。
  • 越权与数值幻觉：易受 Prompt 注入诱导修改阈值，或在总结中凭空捏造未查询到的财务数字。
❌ 症结：黑盒自由生成不可信、不可复现，业务与财务不敢用
PAIN POINT 03 // 传统问答与工单的断层
“被动问答聊完即止，无执行复核闭环”
  • 被动等待“人找数据”：凌晨设备心跳中断或连续离线时，若无人主动提问，AI 永远沉默。
  • 分析与工单两张皮：聊天窗口给出“建议核查退款”，但缺负责人角色（owner_role）、缺 24h 时限与证据绑定。
  • 缺少下一周期验效：任务勾掉就算完，没人对比下一周期退款率是否回到同城中位数 +2pt 以内。
❌ 症结：停留在“嘴上建议”，无法把诊断转化为真实经营改善

ARCHITECTURAL PARADIGM // 四重架构护城河
把确定性留给代码，把交互留给 Agent

1. 标准化后厨（B 层：确定性指标与四值规则引擎）

先聚合后算比率、NULLIF 零保护、按门店中位数算区域 ROI；严格执行 unavailable → insufficient → possible → none 判定序，彻底消灭假阴性。

2. 受控服务员（C 层：7 工具白名单 + 双向防幻觉护栏）

严禁写 SQL 或改阈值！输出护栏通过 collectAllowedNumbers 逐字比对工具证据池，出现任何未授权数字立即熔断回退，保障 100% 零数值幻觉。

3. 高性能上下文（KV Cache 六大铁律 + 三层记忆）

静态前缀 deepFreeze 零插值、Append-Only 消息轨迹、禁滑动窗口截断、采用 SHA-256 持久化摘要压缩，兼顾高缓存命中率与跨轮次指代消解。

4. 全天候巡检员（IoT 主动监控 + 人机协同复核）

设备离线 5 分钟自动告警并唤醒 Agent 审计，15 分钟未确认自动升级；经营动作需人工确认并在下一周期复核指标。
